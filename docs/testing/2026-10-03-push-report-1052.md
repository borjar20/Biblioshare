## Resultado y unidades

`sendPushToUser(s)` devuelve un `PushSendReport`. El outcome interno `sent` del transporte se presenta en el reporte como **`accepted`**: el proveedor aceptó el mensaje. No acredita recepción, visualización ni lectura en el teléfono; un teléfono apagado puede tener un ACK del proveedor.

| Campo | Unidad y significado |
|---|---|
| `users.requested` | Usuarios distintos dentro de una llamada al dispatcher; ids repetidos se deduplican como antes. |
| `users.accepted` | Usuarios con al menos un dispositivo aceptado; dos dispositivos aceptados siguen siendo un usuario. |
| `users.noDevices` | Usuarios cuya consulta terminó correctamente sin dispositivos activos. |
| `users.skipped` | Usuarios cuyos dispositivos se descartaron todos por preferencia o transporte. |
| `users.failed` | Usuarios sin ACK y con algún resultado inválido o temporal. |
| `users.lookupFailed` | Usuarios para los que no pudo consultarse el estado; no se clasifican como `noDevices`. |
| `devices.total/accepted/invalid/temporaryErrors/skipped` | Resultados por dispositivo dentro de la llamada; los cuatro estados suman `total`. |

Las cinco categorías de usuario (`accepted`, `noDevices`, `skipped`, `failed`, `lookupFailed`) son excluyentes y suman `requested`. Un usuario parcialmente aceptado pertenece a `accepted`, conservando los errores de sus otros dispositivos en el recuento de dispositivos.

El barrido devuelve `{ claimed, unknownKind, pushRequests, deviceResults }`. `claimed` y `unknownKind` cuentan **filas del claim**. `pushRequests` suma una solicitud por fila válida; no promete usuarios distintos en todo el barrido. `deviceResults` suma los resultados por dispositivo **y solicitud**. Si dos filas reclaman el mismo usuario, se conservan ambos envíos y se cuentan dos solicitudes; no se añade deduplicación ni otro claim. Un rechazo inesperado del sender se cuenta como una solicitud fallida y no acredita dispositivos aceptados.

La ruta devuelve y loguea el reporte completo, solo cuando hay filas reclamadas, sin nombres, ids ni tokens. Desaparece el ambiguo `sent`, que antes contaba intentos.

Ejemplo verificado: tres claims, dos dispositivos aceptados del primer usuario, un inválido y un temporal del segundo, y ningún dispositivo del tercero:

```json
{
  "claimed": 3,
  "unknownKind": 0,
  "pushRequests": { "requested": 3, "accepted": 1, "noDevices": 1, "skipped": 0, "failed": 1, "lookupFailed": 0 },
  "deviceResults": { "total": 4, "accepted": 2, "invalid": 1, "temporaryErrors": 1, "skipped": 0 }
}
```
